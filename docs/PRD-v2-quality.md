# light-trans v2 PRD：让译文“像人写的中文”

## 定位
面向学生、Chrome 重度用户的 AI 翻译插件，主要读英文科技论文和技术博客（例：Anthropic / Claude Code 官方博客、arXiv 论文）。
只做三件事，做到极致：**PDF 论文翻译、整页翻译、划词/单句翻译**。其他功能不新增。

## 核心问题（用户反馈：DeepSeek 译文生硬）
代码现状诊断（background.js）：
1. Prompt 是“translation engine / preserve tone”，诱导逐字直译，没有“写成地道中文技术文章”的要求。
2. 整页 / PDF 每批 8 段独立翻译，模型不知道文章标题、主题、领域，也看不到前后文。
3. 无术语表：同一术语（agent、harness、prompt caching、context window…）在不同批次译法不一致。
4. 批量要求 JSON id 映射输出，模型注意力被格式占用，句子更机械。
5. temperature 0.1 + 无风格指引。

## 需求（按优先级）

### P0 文档级上下文（整页 + PDF 都要）
- 翻译开始前提取**文档简报**：标题、（论文）摘要或（网页）首段/meta description、站点/领域。
- 用一次轻量 LLM 调用（或从首批结果顺带）生成**术语表**：10–40 个关键术语 → 统一译法；专有名词/产品名/模型名/代码标识符保留英文（如 Claude Code、MCP、token、prompt）。术语表缓存到该文档的生命周期内，所有批次共享。
- 每个批次的请求带上：文档简报 + 术语表 + **前文 1–2 段原文（仅作参考，不翻译）**。
- 缓存 key 要考虑：上下文变化不应导致缓存全失效（可只用 model+target+text+prompt 版本号）。

### P0 重写翻译 Prompt（中文目标语为主，其他语言保持通用）
- 角色：资深中文科技译者/编辑，面向中国大学生和工程师读者。
- 原则：意译优先于直译；按中文习惯重组语序，拆分英文长句，避免“被”字句和“的的的”堆叠，避免“进行……的操作”这类翻译腔；术语首次出现可用“中文（English）”；保持段落信息不增不减。
- 单句/划词：短语给最常用译法；完整句子按上面风格；可利用页面上下文（所在段落）消歧。
- 批量输出格式：保留可靠解析，但推荐用带编号分隔符（如 `<<<s0>>>`）或 JSON，择一实现稳健且不影响质量的方案；保留 <b>/<i> 标签能力和失败回退逻辑。

### P1 批次策略
- 默认按字符预算分批（如 ~2500–3500 字符/批），同一批尽量是连续段落，保证模型看到连贯上下文；并发保持。
- PDF 跨页段落缝合后再分批（已有缝合逻辑，确认与新分批兼容）。

### P1 划词翻译带上下文
- 选中文本时，把所在段落（截断到 ~600 字符）和页面标题作为上下文传给模型，只翻译选中部分。

### P2 设置项
- 选项页新增“译文风格”：`流畅意译（默认）/ 忠实直译`。
- 现有 extraInstructions 保留，附加在后。

## 非目标
不加新翻译场景、不换 UI 框架、不加账号体系。

## 验收标准
1. 用 https://www.anthropic.com/engineering 下任一篇 Claude Code 文章和一篇 arXiv PDF（如 https://arxiv.org/pdf/1706.03762）手测（若无法联网调用 LLM，至少用单元级脚本验证 prompt 构造与解析）。
2. 同一文档内术语译法一致。
3. 批量解析失败率不升高：保留现有逐条回退。
4. 无控制台报错；manifest 权限不新增（除非必要并说明）。
5. README 增补“翻译质量设计”一节；提交为一个或数个清晰的 commit（中文 message，风格同 git log）。
